# Аудит репозитория WALLET

Репозиторий Alexkkkkk/WALLET представляет собой локальную утилиту на Python для восстановления пароля к legacy-кошельку Bitcoin Core (wallet.dat, Berkeley DB, метод деривации 0). Проект включает CLI и GUI на Tkinter, а также экспериментальные AI-модули для генерации словарей. Ниже приведён аудит по ключевым аспектам безопасности, архитектуры и качества кода.

---

## 1. Назначение и архитектура

Проект чётко позиционируется как инструмент для собственного кошелька с обязательным подтверждением владения. README содержит явные предупреждения: не загружать реальные wallet.dat, словари и пароли в публичные места, работать офлайн, использовать только резервные копии, закрыв Bitcoin Core.

Архитектура модульная:

- `crypto.py` — KDF, AES-256-CBC, проверка secp256k1.
- `bdb.py` — изолированное чтение BDB-копии.
- `serialize.py` — bounds-checked парсинг записей.
- `cli.py` / `gui.py` / `runner.py` — интерфейсы и фоновый движок.
- `plan.py` и `ai/` — диагностика и генерация кандидатов.

**Плюсы:** разделение ответственности, единый контракт версии и флагов, тесты на синхронизацию CLI/GUI/README.

**Замечания:** AI-слой и Hashcat-адаптер увеличивают поверхность атаки, но по умолчанию отключены или требуют явного подтверждения.

## 2. Криптографическая безопасность

### 2.1. KDF (SHA-512)

Реализация соответствует Bitcoin Core method 0:

```python
digest = sha512(password + salt)
for _ in range(iterations - 1):
    digest = sha512(digest)
key = digest[:32]; iv = digest[32:48]
```

Это корректно: соль добавляется только на первом раунде, затем хешируется предыдущий дайджест. Ошибок нет.

**Риск:** SHA-512 без HMAC уязвим к length-extension, но в данном контексте (KDF для AES) это не критично, так как злоумышленник не контролирует соль и не может предсказать ключ.

### 2.2. AES-256-CBC и padding

Используется pycryptodome с PKCS#7. Проверка дополнения:

```python
pad = plain[-1]
if not 1 <= pad <= 16 or plain[-pad:] != bytes([pad]) * pad:
    return None
```

Код возвращает `None` при неверном padding, не раскрывая деталей. Это устраняет padding oracle в рамках данного инструмента, поскольку злоумышленник не получает обратной связи о валидности padding (только о том, что пароль не подошёл).

**Остаточный риск:** AES-CBC без аутентификации теоретически подвержен bit-flipping, но в Bitcoin Core целостность косвенно проверяется через вычисление публичного ключа из расшифрованного секрета. Если бит-флиппинг изменит секрет, производный публичный ключ не совпадёт с ckey, и пароль будет отвергнут. Таким образом, проверка `verify_master_key` действует как аутентификатор.

### 2.3. Проверка secp256k1

Всегда вычисляется публичный ключ из расшифрованного 32-байтного секрета и сравнивается с `entry.pubkey` через `hmac.compare_digest` (защита от timing-атак). Опции отключить проверку нет, что соответствует best practices.

**Замечание:** `public_key()` проверяет, что скаляр находится в диапазоне (0, N), где N — порядок secp256k1. Это предотвращает ошибки, но не является уязвимостью.

## 3. Безопасность работы с Berkeley DB

`bdb.py` реализует безопасное чтение:

- Исходный файл не открывается для записи.
- Создаётся временная копия с правами 0600.
- Копия открывается в режиме `DB_RDONLY`.
- После копирования проверяется, что размер и mtime исходника не изменились (защита от активного изменения базы).

**Плюсы:** исключено случайное повреждение оригинала; временный каталог автоматически удаляется.

**Риски:**

- Временная копия может остаться на диске при аварийном завершении (хотя `TemporaryDirectory` обычно очищается).
- На Windows права 0600 не гарантируют ACL, о чём сказано в README.
- Не проверяется целостность BDB-страниц (циклические ссылки, переполнение). Для вредоносного wallet.dat возможен DoS через исчерпание памяти или зацикливание. В Bitcoin Core подобная проблема обсуждалась (PR #35150). Рекомендуется добавить лимиты на размер записей и количество страниц.

## 4. Безопасность CLI и GUI

### 4.1. Обработка паролей и словарей

- Словарь читается в бинарном режиме, снимается только `\n` или `\r\n`; пробелы и пустые строки сохраняются.
- Пароль сохраняется эксклюзивно с флагом `O_EXCL` и правами 0600, без перезаписи существующих файлов.
- При отсутствии `--save` пароль выводится в терминал как bytes и hex, что может попасть в историю. README предупреждает об этом.

**Рекомендация:** для CLI добавить предупреждение при выводе пароля в stdout или требовать явный флаг `--print-password`, чтобы снизить риск случайной утечки.

### 4.2. Многопроцессорность и остановка

`runner.py` использует `multiprocessing.Pool` с `imap_unordered` и `chunksize=1`, что позволяет опрашивать результаты с таймаутом и реагировать на `stop()`. Остановка неблокирующая, пул завершается через `terminate()`.

**Риск:** `terminate()` может оставить дочерние процессы в зомби-состоянии, если они не завершатся. В коде вызывается `pool.join()` после `terminate()`, что обычно достаточно, но при зависании нативного драйвера BDB процесс может не убиться. Рекомендуется добавить таймаут на `join()`.

### 4.3. Tkinter GUI

GUI не выполняет сетевых запросов, использует локальные файлы. Ввод ограничивается полями и файловыми диалогами. Потенциальных инъекций нет.

**Замечание:** GUI сохраняет пароль через ту же функцию `save_password`, что и CLI, с правами 0600. Это корректно.

## 5. AI-модули и сетевые взаимодействия

По умолчанию AI-провайдер — `offline`, сеть не используется. Ollama вызывается только по 127.0.0.1:11434. OpenAI выбирается явно и передаёт текст воспоминаний внешнему провайдеру, о чём есть предупреждение.

**Риск:** при выборе OpenAI конфиденциальные воспоминания покидают машину. Это документировано, но можно добавить дополнительное подтверждение в GUI (чекбокс «Я понимаю, что текст будет отправлен»).

## 6. Потенциальные уязвимости и рекомендации

| Область | Риск | Уровень | Рекомендация |
|---|---|---|---|
| BDB-парсер | DoS через циклические ссылки или огромные записи | Средний | Добавить лимиты на размер записи и глубину страниц; отклонять циклические ссылки |
| AES-CBC | Bit-flipping (теоретически) | Низкий (смягчено проверкой pubkey) | Оставить как есть; проверка ключа достаточна |
| CLI stdout | Утечка пароля в историю терминала | Низкий | Требовать явный флаг для вывода пароля |
| Временные файлы | Остаток копии при сбое | Низкий | Использовать TemporaryDirectory с delete=True (уже так) и добавить очистку при SIGINT |
| Tkinter | Нет | — | — |
| Сетевой AI | Утечка данных при OpenAI | Средний | Добавить подтверждение в GUI |
| Hashcat | Потенциальная утечка potfile | Средний | README уже предупреждает; можно добавить автоматическую установку прав 0600 на state-dir |

## 7. Качество кода и тесты

- Код читаемый, с docstring и комментариями.
- Есть модульные и интеграционные тесты, включая проверку синхронизации флагов CLI/GUI/README.
- CI прогоняет тесты на Python 3.10–3.12.
- Используются `hmac.compare_digest`, `os.O_EXCL`, `0o600` — признаки внимания к безопасности.

**Недостаток:** тесты не покрывают вредоносные BDB-файлы (fuzzing). Рекомендуется добавить фаззинг `serialize.py` и `bdb.py`.

---

## Итоговая оценка

Проект демонстрирует хороший уровень безопасности для инструмента такого класса. Критические уязвимости не обнаружены. Основные остаточные риски связаны с DoS через специально сформированный wallet.dat, утечкой пароля через stdout и потенциальной передачей данных при выборе OpenAI. Все они либо смягчены, либо документированы. Рекомендуется добавить ограничения на размер записей BDB и дополнительное подтверждение для сетевого AI.
